\chapter{Related work} \label{sec:related_work}

As sparse kernels become pervasive, a large body of work has emerged on their performance analysis and optimization, spanning both hardware and software techniques. This chapter positions the contributions of this thesis with respect to three gaps in the literature. First, existing characterization studies focus primarily on individual kernels such as SpMV, leaving broader sparse tensor workloads and machine learning embedding operations less thoroughly understood. Second, existing architectures tend to trade off performance against flexibility: incremental CPU optimizations preserve programmability but deliver limited speedups, while custom accelerators provide high performance only for narrow kernels. Third, DAE architectures expose a challenging programming model, and existing compiler techniques do not automatically generate optimized DAE code for the sparse-dense operations that arise in modern machine learning workloads.

\section{Performance Analysis of Sparse Workloads}

Because of its unique characteristics, sparse computation has been widely studied. However, existing performance analyses mostly focus on SpMV kernels. Less attention has been dedicated to sparse kernels with more complex traversal and merging behavior, or to sparse machine learning workloads with different locality properties.

\subsection{Performance Analysis of SpMV}
SpMV is one of the most critical kernels in scientific computing, and its performance has been extensively studied, particularly on CPUs. Mantovani et al.~\cite{mantovani2020benchmark} evaluate thread- and node-level scalability on the MareNostrum4 supercomputer and ThunderX2-based systems, comparing both performance and energy consumption across microarchitectural choices such as vector unit width and cache hierarchy design. Armejach et al.~\cite{armejach2019hpc} analyze a range of HPC processors employing different combinations of in-order and out-of-order cores as well as varying last-level cache capacities per core, concluding that scaling last-level caches yields diminishing returns while substantially increasing area and power. Oliveira et al.~\cite{oliveira2021damov} compare HPC processors using metrics including GFLOPS per Watt, GFLOPS versus memory bandwidth, and bytes per FLOP.

Other studies focus on the data movement and format choices that shape SpMV performance. Bean et al.~\cite{bean2015gdma} characterize data movement in memory-intensive benchmarks using metrics such as MPKI, last-to-first-level cache ratios, and operational intensity. Asgari et al.~\cite{asgari2021copernicus} discuss the performance implications of different sparse matrix representations, while Alappat et al.~\cite{alappat2022spmv} evaluate SpMV and lattice quantum chromodynamics kernels on the A64FX platform, comparing the impact of multiple formats. As GPUs have become increasingly prominent in HPC, several authors have also investigated SpMV performance on them~\cite{bell2009spmv}. More recently, Nguyen et al.~\cite{fpga2022ccpe} analyze SpMV performance on off-the-shelf CPUs, GPUs, and FPGAs, demonstrating that indirect lookups into the dense vector remain a dominant bottleneck across all three architectures.

Together, these studies establish SpMV as a memory-bound sparse-dense kernel whose performance is limited by irregular access to the dense input vector. However, they do not fully characterize the broader set of traversal, merging, and lookup patterns that appear in sparse tensor algebra and sparse machine learning workloads.

\subsection{Performance Analysis of Other Sparse Kernels}
Despite the extensive body of work on SpMV, comparatively little effort has been devoted to examining more complex sparse kernels such as SpADD or SpGEMM~\cite{gao2023spgemm_survey}, which introduce additional challenges---including more irregular control flow, more complex merging behavior, and heavier reliance on intermediate data structures.

\subsection{Performance Analysis of Embedding Operations}
With the rise of sparsity and feature embeddings in machine learning, several authors have begun examining their architectural implications. Gupta et al.~\cite{dlrm2020hpca} show that the embedding bag function in DLRMs suffers from memory bottlenecks analogous to scientific kernels, despite having different spatio-temporal locality characteristics. Zaheer et al.~\cite{bigbird2024neurips} highlight the inefficiency of loading sparse attention blocks in LLMs on conventional architectures. However, none of these studies analyze performance at the microarchitectural level, nor do they characterize these workloads in ways that provide actionable guidance for designing more efficient architectures.

\subsection{Our Performance Characterization}
To overcome these limitations, in \Cref{sec:architectural-implications-of-sparsity} we characterize sparsity across both scientific and machine learning workloads. We start, in \Cref{sec:architectural-implications-of-sparsity-scientific-computing}, with a performance analysis of a broad suite of sparse tensor algebra kernels in scientific computing, including SpMV, SpGEMM, and SpADD, evaluated on a large set of matrices and diverse processor architectures. Then, in \Cref{sec:architectural-implications-of-sparsity-in-machine-learning}, we extend this characterization to a large set of embedding operations and use the results to identify the architectural properties needed by these workloads.

\section{Architectures Optimized for Sparse Computation}

Because of their importance, several authors have proposed architectures to accelerate sparse workloads. These architectures fall into four broad categories: incremental optimizations to conventional processors, fixed-function sparse accelerators, flexible sparse tensor accelerators, and DAE-style systems that separate access from execution. These designs make different trade-offs among performance, flexibility, vector integration, programmability, and data movement. In contrast, this thesis targets a DAE design that combines efficient sparse traversal and merging with general-purpose vector computation.

\subsection{Incremental Optimizations for Sparse Tensor Algebra}
A number of solutions have been proposed to optimize indirect lookups on traditional architectures. Programmable prefetchers~\cite{yu2015, AinsworthJ16, talati2021prodigy} allow software to describe a restricted set of access patterns for the hardware to prefetch, including the indirect access in SpMV. Data layout transformation mechanisms reorganize sparse data into denser formats to improve locality and better exploit the memory hierarchy~\cite{dre, planar2021acm, impulse}. Vector extensions such as Tarantula~\cite{tarantula} extend support for non-unit-stride accesses and improve the efficiency of gather/scatter instructions. These proposals preserve the conventional programming model and require limited hardware changes, but they support only limited classes of access patterns---largely those arising from SpMV---and do not address the data-dependent control flow required by sparse merging.

A more general approach is the streaming abstraction proposed by Scheffler et al.~\cite{scheffler2021stream,scheffler2023stream,scheffler2024stream,scheffler2025occamy,zhang2023axipack,manoni2025spikestream}. The authors extend the RISC-V instruction set to support streaming abstractions for indirect accesses and merging. The core can program these streams to load and merge sparse and dense tensors, then pop the resulting data for computation. This offloads indirect accesses and control flow from the compute pipeline, achieving substantial performance improvements. While this solution can accelerate a larger set of sparse algebraic kernels, it mostly targets scalar cores rather than state-of-the-art vector cores, leaving performance on the table.

\subsection{Fixed-Function Architectures for Sparse Tensor Algebra}
At the opposite end of the design spectrum lie fully custom architectures for sparse tensor algebra. Several architectures have been proposed to accelerate SpMV-like workloads, including FPGA-based designs~\cite{fowers2014spmv,grigoras2015spmv,umuroglu2014spmv}, fixed-function architectures~\cite{nurvitadhi2015spmv,zhang2020sparch,sadi2019spmv}, and processing-in-memory systems~\cite{giannoula2022sparsep}. Designs such as GAMMA~\cite{zhang2021gamma} and related systems~\cite{srivastava2020matraptor,pal2018outerspace,zhang2020sparch,lin2010spmv,quin2020sigma,parashar2017sparse,zhang2016cambriconx} implement fixed-function units for sparse matrix--matrix multiplication, a fundamental kernel to which many tensor algebra operations can be reduced. These solutions offer high performance, but their specialization limits flexibility, restricts support for kernel fusion, and often requires substantial data movement between the accelerator and the rest of the system~\cite{bharadwaj2022sparse_for_ml}.

\subsection{Flexible Architectures for Sparse Tensor Algebra}
More flexible architectures, such as Capstan~\cite{rucker2021capstan} and others~\cite{dadu2019spu,hegde2019extensor,asgari2020alrescha,hwang2020centaur,mishra2017sparse,nurvitadhi2016sparse}, can be programmed to execute a wider range of Einsum expressions~\cite{sam2023asplos}. Despite their broader applicability, computation on specialized hardware remains constrained by design choices such as a restricted set of operations, data types, and memory capacity. Moreover, using such accelerators typically requires moving tensors into and out of accelerator memory before and after every computation. In real-world applications such as CP-ALS tensor decomposition~\cite{phipps2019genten}, where intermediate results must be evaluated at each iteration, this overhead can outweigh the benefits.

\subsection{Hardware-Software Co-Design and DAE Architectures}
To address these limitations, DAE architectures combine specialized access units with general-purpose compute cores. Maple~\cite{maple2022isca} uses specialized access units to accelerate indirect memory accesses for a scalar core. Similarly, HATS~\cite{hats} and SpZip~\cite{spzip2021isca} employ dedicated access units to accelerate graph traversals: HATS exploits graph locality to reduce data movement, while SpZip applies compression and decompression techniques to lower memory traffic. Smash uses a custom engine to decompress sparse matrices stored in a custom compressed format~\cite{kanellopoulos2019smash}. Cambricon-S uses a specialized engine to efficiently load weights of sparse neural networks~\cite{zhou2018cambricons}. Unlike programmable prefetchers, which aim to bring data into caches ahead of time, these access units push data directly into hardware or software queues that the compute core consumes, making them more effective for highly irregular access patterns. However, these systems primarily target specific access patterns and are restricted to scalar cores rather than modern vectorized architectures. They therefore do not provide broad acceleration of sparse traversal and merging while preserving the performance of vector computation.

\subsection{Production DAE-Like Architectures}
DAE-like designs that separate memory access from computation are becoming increasingly prevalent among hyperscalers. Meta MTIAs~\cite{mtia2023isca} and Google TPUs~\cite{tpu2023isca} both adopt such an approach to accelerate embedding lookups in recommendation models. Recent Nvidia GPUs~\cite{nvidiah100} similarly include specialized access units, Tensor Memory Accelerators (TMAs), for fetching dense tensor tiles. These designs demonstrate the value of separating access from execution for vector lookups, embedding operations, and dense tile movement. However, they do not target the broader combination of sparse traversal, sparse coordinate merging, and vectorized dense computation required by the sparse tensor workloads studied in this thesis.

\subsection{Our Hardware Architecture: The TMU}
We designed the TMU to close these gaps. As discussed in \Cref{sec:the-tmu}, a multicore DAE processor composed of TMU--CPU cores provides a combination of efficiency and generality not offered by prior designs: the TMU offloads sparse traversal, merging, and marshaling, while the CPU core retains the flexibility and throughput of modern vector execution. \Cref{tab:soa-comparison} qualitatively compares the TMU with state-of-the-art solutions.

\section{DAE Compilation}

One of the primary barriers to widespread adoption of DAE architectures is programmability. In scientific computing, this complexity can often be hidden behind kernel libraries, making hand-written and hand-optimized DAE implementations feasible for a relatively small set of routines. Machine learning workloads are different: embedding operations appear in many variants, formats, reductions, and fusion contexts, making a library-only approach difficult to scale.

\subsection{Traditional Machine Learning Compilers}
Traditional machine learning compilers generate machine code from a semantic representation of the model~\cite{tf2015whitepaper,pytorch2019neurips,caffe2014arxiv,jax2018github,pytorchgeometric2019github,glow2018arxiv}. As in the Meta MTIA ecosystem~\cite{mtia2023isca}, models are decomposed and lowered to handwritten kernels optimized for the target architecture. While effective, this strategy does not scale to the wide variety of embedding operations, their algorithmic complexity, or the combinatorial explosion of input formats, reduction operators, precisions, and algorithmic optimizations such as operator fusion.

\subsection{Tensor Compilers}
Tensor compilers address this challenge by progressively lowering machine learning models through a sequence of IRs until code generation. For example, through MLIR~\cite{mlir2021cgo}, PyTorch programs can be lowered via IRs such as Linalg (i.e., linear algebra kernels like matrix multiplication), SCF (i.e., structured imperative code composed of loops, if-then-else constructs, and memory/compute instructions), and LLVM (i.e., unstructured low-level imperative code composed of branching instructions and memory/compute operations). This enables optimizations at multiple abstraction levels. High-level IRs (e.g., Linalg~\cite{mlir2021cgo}, index notations~\cite{taco2017oopsla,mlirsparse2022taco}, or Einsums~\cite{tf2015whitepaper}) describe what to compute, whereas lower-level IRs describe how to compute it. Although high-level tensor IRs support powerful algorithmic optimizations such as operation fusion~\cite{tf2015whitepaper,pytorch2019neurips,caffe2014arxiv,jax2018github,pytorchgeometric2019github,glow2018arxiv}, their level of abstraction makes them unsuitable for architectural optimizations, including those required for DAE systems. Consequently, most architectural optimizations occur in lower-level IRs (e.g., SCF or LLVM IR~\cite{llvm2004cs}) after high-level algorithmic transformations have already been applied. While tensor compilers have been successfully used for CPUs~\cite{taco2017oopsla,mlirsparse2022taco,looplets2023cgo,mosaic2023pldi,indexstreams2023pldi}, GPUs~\cite{tacoscheduling2020oopsla,sparsetir2023asplos,liu2024unisparse}, FPGAs~\cite{liu2024unisparse}, and distributed systems~\cite{spdistal2022sc}, compilation for tensor DAE systems remains largely unexplored. Lopoukhine et al.~\cite{rvx2025lopoukhine} recently showed the potential of multi-level compilation flows for ISA extensions such as streaming registers, but this technique does not directly apply to complex DAE systems like a TMU--CPU core, where both indexing and memory accesses are fully offloaded to the access unit.

\subsection{DAE Compilation}
Earlier work on DAE compilation~\cite{desc2015micro}, predating modern tensor compilers, explored generating DAE code from LLVM IR~\cite{llvm2004cs}. However, LLVM IR is unstructured and represents loops using conditional branches, making it ill-suited for analyzing the deep loop hierarchies that arise in embedding operations~\cite{panda2020tcad,rvx2025lopoukhine}. For example, identifying loop-offloading candidates (\Cref{sec:lowering-scf-to-slc}) becomes impractical in such representations. High-level synthesis tools address similar challenges using pragmas~\cite{cong2011autoesl,stream2019wang}, but these require user intervention and are incompatible with our automated compilation flow. For affine loops, Jimborean et al.~\cite{dvfs2018jimborean} use polyhedral analysis to overcome these limitations, but this approach cannot be applied to embedding operations. Moreover, unlike our SLC IR, LLVM IR is not designed to represent DAE programs: it cannot express separate access and compute stages, nor can it model data (de)serialization. As a result, optimizations cannot be applied iteratively and must instead be embedded directly into the lowering and code-generation process, which is impractical for sophisticated transformations.

\subsection{Our Compiler: Ember}
To overcome these limitations, in \Cref{sec:dae-compilation} we introduce the Ember compiler, which features custom IRs that lower PyTorch and TensorFlow embedding operations to optimized DAE code. Ember automates DAE-specific optimizations while remaining integrated with modern tensor compiler stacks, enabling users to exploit the TMU without manually writing DAE programs.

\section{Summary}
The literature demonstrates that sparse workloads are important, difficult to accelerate, and increasingly relevant across both scientific computing and machine learning. However, three gaps remain. Existing characterization studies do not provide a unified view of the traversal, merging, and lookup bottlenecks that span these domains. Existing sparse architectures either preserve flexibility with limited speedups or achieve high performance through specialization that constrains programmability, vector integration, or data movement. Finally, existing compiler techniques do not automatically generate optimized DAE code for the diverse sparse-dense embedding operations found in modern machine learning models. This thesis addresses these gaps through a cross-domain characterization, the TMU architecture, and the Ember compiler.

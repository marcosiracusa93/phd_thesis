We address the bottlenecks identified in \Cref{sec:architectural-implications} by designing the Tensor Marshaling Unit (TMU), a specialized access unit for Decoupled Access--Execute (DAE) execution of sparse tensor algebra. The TMU is designed to efficiently perform sparse tensor traversal and merging, then marshals vector operands to the CPU vector units. By mapping irregular operations to the TMU and regular computation to the CPU, these two units can be specialized and optimized independently, improving overall system performance. \Cref{sec:tmu-programming-interface,sec:tmu-microarchitecture} introduce the TMU programming model for decoupled sparse tensor algebra, its microarchitecture, and its integration into a DAE processor. \Cref{sec:tmu-scientific-evaluation,sec:tmu-embedding-evaluation} then evaluate the TMU on scientific sparse tensor algebra and machine learning embedding workloads, including specialized DAE organizations for low-reuse embedding operations.

\section{TMU Programming Interface} \label{sec:tmu-programming-interface} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

This section introduces the TMU, its instruction set, and its usage to accelerate sparse tensor algebra operations. The architecture follows directly from the requirements derived in \Cref{sec:architectural-implications}: Traversal Units (TUs) expose memory-level parallelism for irregular scan-and-lookup operations (\Cref{sec:scan-and-lookup}), Traversal Groups (TGs) perform coordinate merging and loop synchronization, the memory arbiter and TU queues track long-latency requests outside the core~\cite{esmailidokht2024micro}, and the outQ marshals scalar, vector, and predicate operands into the core so computation can still use standard vector execution.

\subsection{TMU Overview} \label{sec:tmu-overview} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\Cref{fig:tmu-architecture-overview} shows the proposed DAE processor---a general-purpose processor that features a TMU per core to decouples memory access and computation into two separate units. Overall, the TMU can be \textcircled{1} programmed to \textcircled{2} traverse and merge tensor operands and \textcircled{3} marshal the aggregated data to the compute core via a memory-mapped output queue (outQ) that the compute core can \textcircled{4} process. Data reads are managed by the TMU memory arbiter, whereas marshaling is managed by the outQ buffer. TMU traversal, merging, and marshaling are programmed with dataflow primitives, whereas the compute code is wrapped in callback functions that the TMU triggers on traversal/merging events. The programming contract is intentionally narrow: the TMU does not execute arbitrary arithmetic, but instead emits an ordered stream of callback IDs and operands. The compute core consumes this stream and executes the corresponding callback code, so the TMU preserves the traversal and event order of the original loop nest.

The outer loop, shown in yellow, traverses the dense CSR fiber of row pointers; the inner loop, shown in blue, scans nonzeros and performs the dense-vector lookup; and the body and tail regions, shown in green, perform arithmetic and final writeback. Because of the format abstraction described in \Cref{sec:tensor-compression-formats}, we can express tensor operations as \emph{dataflow} programs that stream input tensors through traversal, merging, and compute operations~\cite{hsu2023asplos}. With this dataflow abstraction, we can map tensor traversal and merging to the TMU, and computation to the compute core. \Cref{fig:tmu-spmv-decomposition} shows this decomposition for SpMV, where row-pointer traversal and nonzero traversal become TMU work, while multiplication, accumulation, and final writeback remain compute core callbacks.

\noindent\textbf{Traversal units, lanes and layers:}
As shown in \Cref{fig:tmu-architecture-overview}, the TMU is a matrix of Traversal Units (TUs), where each TU implements logic and storage to traverse a tensor fiber, that is, each of the \texttt{for} loops in \Cref{fig:tmu-spmv-decomposition} (lines 3-4 and 5-7). Each of these \texttt{for} loops can be mapped to the TUs of a TMU column, called a \emph{layer}. The \texttt{for} loop in lines 3-4 would map to the left-most layer, producing indices that flow into the second layer, where the \texttt{for} loop in lines 5-7 would be mapped. Therefore, the TMU has a dataflow design that flows rightward. In addition, loop iterations can be parallelized using multiple rows, called \emph{lanes}, which can also be used to load and merge multiple tensors.

\noindent\textbf{Multi-lane parallelism:} The values loaded by multiple lanes, either for parallel traversal or merging, are marshaled into vector operands. For example, each lane of the second layer that is traversing the \texttt{for} loop in lines 5-7 of \Cref{fig:tmu-spmv-decomposition} loads one \emph{vec\_val} and one \emph{nnz\_val}, which are then marshaled into vector operands.

\noindent\textbf{Callbacks and outQ processing:}
These operands are computed by the host core with the callbacks in \Cref{fig:tmu-spmv-callbacks}.
These callbacks wrap the compute code of the body (\emph{ri}) and tail (\emph{re}) regions of the inner loop shown in \Cref{fig:tmu-spmv-decomposition}. The \emph{ri} callback accumulates partial-results (into the \texttt{sum} variable) and is triggered by the TMU at every row iteration (inner-loop body). The \emph{re} callback stores results at the end of every row traversal (inner-loop tail).
To decouple TMU and compute core execution, the TMU sends to the compute core, through the outQ, a control/data stream defining the ordered sequence of callbacks and operands that the compute core should compute.

For instance, running a two-lane SpMV on the CSR matrix in \Cref{fig:background-sparse-compression-formats} would push the following control/data sequence into the outQ:
\begin{small}
\begin{verbatim}
ri AB ab ri C0 c0 re re ri DE cd re re ri FG de ri H0 f0 re
\end{verbatim}
\end{small}
In this notation, \texttt{ri} and \texttt{re} are callback IDs, uppercase letters denote nonzero matrix values, lowercase letters denote dense-vector values, and \texttt{0} marks an inactive lane introduced by padding or masking. This sequence triggers two accumulations for the first row, none for the second row (since empty), and so on.

\Cref{sec:tmu-programming-traversal,sec:tmu-programming-merging-vectorization,sec:tmu-marshaling-computation,sec:tmu-mapping} illustrate how to program the TMU to run parallel traversal and merging of Einsum expressions.

\subsection{Programming Tensor Traversal} \label{sec:tmu-programming-traversal} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

As described in \Cref{sec:tensor-traversal}, all sparse and dense fiber traversals have the following \texttt{for} loop structure:

{\small
\begin{verbatim}
    for(i=beg; i<end; i+=stride)
\end{verbatim}
}

Each TU provides the logic and storage to iterate such a loop, with \texttt{beg} and \texttt{end} defined by the fiber traversal, and load fiber values into streams.

\noindent\textbf{Fiber iteration:}
\Cref{tab:tmu-isa-traversal-primitives} shows the primitives we can use to program TUs to implement the traversals in \Cref{sec:tensor-traversal}.
For instance, we can use a \texttt{Dense} primitive to implement the outer loop of SpMV in \Cref{fig:tmu-spmv-decomposition}, to iterate through matrix rows and load the row pointers.
These pointers, loaded into streams, are then used to implement the inner-loop traversal, with a \texttt{Range} primitive, to load nonzero values and column indices (compressed levels), which, in turn, are used to load dense vector values through scan-and-lookup.
SpMM ($Z_{ij}=A_{ik}B_{kj}$), instead, works similarly but requires an additional inner loop, implemented with an \texttt{Index} primitive, to scan entire rows of the right-hand side matrix ($B_k$).

\noindent\textbf{Data loading:}
Once the iteration space of a TU is defined, data loading is implemented through the \emph{data streams} listed in \Cref{tab:tmu-isa-data-streams}.
The \texttt{mem} stream loads data from a base address and a stream of indices.
To generate the index stream, TUs push their current iteration index (i.e., loop induction variable) into an \texttt{ite} stream, which can also be transformed with \texttt{lin} or \texttt{map} streams. Indirect accesses can be implemented by chaining \texttt{mem} streams.
Hence, we can represent a fiber traversal with a \textit{parent}-\textit{children} dependency tree where the \texttt{ite} stream is the \textit{root}.
For instance, the SpMV scan-and-lookup operation in \Cref{fig:tmu-spmv-decomposition} is implemented by instantiating two \texttt{mem} streams: a parent stream that loads the column indices, which are then used by its child stream to index into the dense vector.

\subsection{Programming Merging and Vectorization} \label{sec:tmu-programming-merging-vectorization} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

We can use multiple TMU lanes to parallelize loop traversal or merge different tensors.
Parallelization and merging can happen at any tensor level by setting TMU layers to one of the configurations shown in \Cref{tab:tmu-isa-layer-modes}.

\noindent\textbf{Parallelization} is achieved by distributing loop iterations across different lanes.
Overall, parallelization enables (1) parallel loading, reducing the control overhead of traversing compressed data structures, and (2) parallel marshaling, enabling efficient vectorized compute in the host core.
The two-dimensional TMU design allows loops to be parallelized at different levels.
For instance, inner-loop parallelization allows the TMU to marshal adjacent tensor elements into the same vector operand (i.e. the usual vectorization scheme).
Outer-loop parallelization, instead, allows the TMU to marshal multiple fibers, slices, and arbitrary tensor dimensions into the same vector operand, enabling higher-dimensional parallelization schemes.
In the SpMV example in \Cref{fig:tmu-spmv-decomposition}, where we parallelize at the inner-loop level, we configure the first layer to load row pointers and \texttt{BCast} them to the next layer.
The second layer then loads multiple elements of the same row in \texttt{LockStep}, with each lane starting at a different offset and advancing by the number of active lanes so that lanes cover disjoint nonzeros.
To parallelize SpMV at the outer-loop level, concurrently loading multiple rows into different lanes, both layers work in \texttt{LockStep}.
Both parallelization schemes aggregate data into vector operands that are marshaled into the core for computation.
Boundary conditions can be handled by padding or marshaling the \texttt{msk} stream along with the operands, indicating the active elements in a multi-hot bit vector (equivalent to the \texttt{svwhilelt} operation in Arm SVE~\cite{stephens2017micro}).

\noindent\textbf{Fiber merging} is achieved by loading different tensors in different lanes and merging them hierarchically with the mergers placed between layers.
Merging operations are implemented by sorting the fiber indices produced by the active lanes of a TMU layer, which is achieved by iteratively pulling fibers with minimum indices.
The position of these fibers can be identified with a multi-hot $l$-bit predicate, which is pushed in the \texttt{msk} stream of the layer.
For the two-lane merging example in \Cref{fig:background-sparse-fiber-merging}, the \texttt{msk} stream is \texttt{11, 01, 10, 11}, with the first bit representing fiber A and the second bit representing fiber B.
These predicates are then used to aggregate vector operands to send to the core.
In this way, for instance, we can implement SpKAdd~\cite{hussain2022ipdps}, a summation of K sparse matrices, by mapping matrices in K different lanes and merging them with \texttt{DisjMrg} layers.
\Cref{fig:tmu-spkadd-callback} shows the compute code of SpKAdd: the TMU traverses all the K matrices row by row and, for each row, sends to the core all nonzero values with the same index, which are reduced with a vector operation.
Running SpKAdd on the two rows in \Cref{fig:background-sparse-fiber-merging} would produce the following vector operand stream: \texttt{AB C D EF}, with \texttt{AB} and \texttt{EF} being reduced in the core.
If matrices are in CSR format, only the second compressed dimension requires merging.
In contrast, if matrices are in DCSR format, both dimensions are compressed and both need to be merged.
In this latter case, the merge happens hierarchically: only the active lanes from the first dimension, which are identified by the \texttt{msk} predicate of the first layer, are merged in the second layer.

\subsection{Data Marshaling and Computation} \label{sec:tmu-marshaling-computation} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Once we map the loop structure of a tensor expression into TMU layers, the TMU streams the aggregated data to the core for computation. Core compute is enabled by wrapping the compute code within the \textit{head} (H), \textit{body} (B), and \textit{tail} (T) regions of traversal/merging loops into callback functions. % of a tensor expression.
These callback functions have a unique callback ID and a list of scalar, vector, or predicate operands produced by the TMU.
In the SpMV example in \Cref{fig:tmu-spmv-decomposition}, we wrap the code in the inner-loop body into a \texttt{ri} callback, which multiplies and accumulates the matrix and vector values provided by the TMU, and the code in the inner-loop tail into a \texttt{re} callback, to store the accumulated results.

Each TMU layer can be programmed to trigger callbacks upon traversal or merging events, such as the \textit{begin}, \textit{iteration}, and \textit{end} events of the traversal assigned to that layer.
In the SpMV example in \Cref{fig:tmu-spmv-decomposition}, we register the \texttt{ri} callback to the \textit{iteration} event of the TMU layer that traverses the nonzeros of a CSR row (the inner loop), and the \texttt{re} callback to the \textit{end} event of that same inner-loop traversal.
For the \texttt{ri} callback, we also register the list of operands consisting of matrix and vector values. Callback registration can be done with the following operation:

{\small
\begin{verbatim}
    add_callback(event, callback_id, args_list)
\end{verbatim}
}

While running, the TMU pushes the callback IDs and vector operands of each registered event into the current outQ chunk.
When the chunk is full, the compute core starts reading callback IDs and executes the proper HBT callback to compute the data operands.
Meanwhile, the TMU populates another outQ chunk, overlapping data loading and computation.

\section{TMU Microarchitecture} \label{sec:tmu-microarchitecture} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

This section explains how the TMU executes the programming abstractions introduced above.
We first describe how Traversal Units iterate tensor fibers and produce synchronized data and control streams.
We then describe how Traversal Groups merge or co-iterate lanes within each layer, how the memory subsystem supports many outstanding sparse accesses, and how the TMU stores architectural state for context switching.
Finally, we walk through the execution of a column-parallel SpMV example to connect these mechanisms end to end.

\subsection{Traversal Unit Design} \label{sec:tmu-traversal-unit-design} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Each TU contains a set of data streams and a control stream, all implemented as circular queues.
Data streams carry iteration variables and values produced by memory or arithmetic operations, such as tensor values, tensor indices, memory addresses, and transformed indices or addresses.
The binary control sequence marks fiber boundaries for the synchronized data streams: a \texttt{0} token denotes a regular iteration element, and a \texttt{1} token denotes the end of the current fiber.

All data streams within the same TU have the same depth and advance together with the TU control sequence through synchronized push and pull operations.
Hence, each queue entry is computed from the corresponding entry at the same position in its parent stream, as defined in \Cref{sec:tmu-programming-traversal}.
This synchronization allows a TU to produce related streams in parallel; for example, in SpMV it can concurrently load column indices and nonzero values for the same CSR row entry.

With this organization, TUs implement the logic to (i)~iterate tensor fibers, (ii)~generate a binary control sequence to track the iteration status, and (iii)~populate data streams with memory or arithmetic operations.
To iterate a tensor fiber, each TU implements a finite-state machine (FSM) looping through the \texttt{fbeg}, \texttt{fite}, and \texttt{fend} states.
The \texttt{fbeg} state initializes the iteration boundaries, which can either be constant values or read from a leftward TU, stalling the current TU execution if the leftward TU has not produced new valid data yet.
If the streams are not full, the \texttt{fite} state pushes (i)~a \texttt{0} token into the binary control sequence, (ii)~the current iteration index into the \texttt{ite} stream, and (iii)~a new element into each other stream (which is generated according to the stream type).
As discussed below, the value of this element depends on its input queue.
Finally, when the fiber traversal has no more elements to iterate, the \texttt{fend} state pushes a \texttt{1} token into the binary control sequence and returns to the \texttt{fbeg} state.

If the parent queue implements a \texttt{mem} stream, its value may not be available immediately because of memory latency, leaving some queue elements in a transient state. In particular, queue elements can be in either a \texttt{valid} or \texttt{waiting} state according to whether the corresponding element in the parent queue is valid. Elements of \texttt{mem} queues, instead, can be in a \texttt{waiting}, \texttt{queued}, \texttt{requested}, or \texttt{valid} state according to whether the parent index is not valid, the address has been computed, the request has been submitted to memory, or the data has returned, respectively.
This per-entry state tracking is central to the TMU's dataflow design: independent queues can continue generating addresses and issuing memory requests while other queue entries wait for their operands or memory responses, allowing the TMU to sustain many outstanding sparse memory accesses.

\subsection{Traversal Group Design} \label{sec:tmu-traversal-group-design} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

A Traversal Group (TG) corresponds to one TMU layer in \Cref{fig:tmu-architecture-overview}: it includes the TUs in that layer, which implement different lanes, and the associated merger logic.
The TG implements the logic to merge and co-iterate these TUs.
Similarly to TUs, TGs also implement an FSM to loop through \texttt{gbeg}, \texttt{gite}, and \texttt{gend} states, generating predicates and a control sequence. The output predicate is the layer predicate later exposed through the \texttt{msk} stream. The control sequence is used later on to trigger callbacks.

TG FSMs compute their control sequence by combining (i) the predicate of the previous layer, if any, and (ii) the control sequences of all the TUs in the layer, implementing a hierarchical evaluation.
In particular, we consider a lane to be \emph{active} only if the corresponding bit of the predicate coming out of the previous layer is set to true.
TGs only process a \texttt{gite} state if all the active lanes have valid data in their queue heads.

In disjunctive merging, the \texttt{gite} state (i) computes the output predicate by setting the active lanes with minimum indices to \texttt{1}, (ii) consumes them, and (iii) pushes a \texttt{0} token into the binary control sequence.
When all active TUs have no more elements to merge disjunctively, the \texttt{gend} state pushes a \texttt{1} token into the binary control sequence.

\input{fig_spmv_sbs_example}

In conjunctive merging, the \texttt{gite} state (i)~computes the output predicate by setting active lanes with minimum indices to one, (ii)~consumes them, and (iii)~pushes a \texttt{0} token into the binary control sequence only if all active lanes have minimum indices (all-true predicate).
When any active TU has no more elements to merge conjunctively, the \texttt{gend} state pushes a \texttt{1} token into the binary control sequence.

Finally, in lockstep co-iteration, the \texttt{gite} state (i) computes the output predicate by setting active lanes that have not finished iterating to one, (ii) consumes their heads, and (iii) pushes a \texttt{0} token into the binary control sequence.
When all active TUs have no more elements to co-iterate, the \texttt{gend} state pushes a \texttt{1} token into the binary control sequence.

\subsection{Output Queue Construction} \label{sec:tmu-output-queue-construction} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The predicates and control sequences generated from each TG are then used to push callback IDs and operands into the outQ.
Similarly to traversal and merging, outQ construction is implemented as an FSM running in each TG.
However, while traversal and merging phases can be fully decoupled (i.e., each TU/TG iteration can start as soon as it has valid inputs), outQ generation needs to be serialized across TGs to preserve the order in which callbacks and operands are processed by the compute core (analogous to out-of-order execution and in-order commit implemented in today's processors).
Hence, besides the \texttt{obeg}, \texttt{oite}, and \texttt{oend} states, outQ generation also requires \texttt{ow4p} and \texttt{ow4n} states to signal that a TG is waiting for the previous or next TG to push data into the outQ.
When a TG is in a \texttt{gbeg}, \texttt{gite}, or \texttt{gend} state, it checks whether any callback is associated with that state and, if so, pushes its ID and operands into the outQ buffer.
For performance reasons, both the outQ and outQ buffers are double-buffered.

\subsection{Memory Arbiter} \label{sec:tmu-memory-arbiter} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The TMU sends out memory requests at the cacheline granularity.
Each cycle, the TMU memory arbiter selects at most one cacheline request by walking a fixed priority hierarchy.
It first prioritizes requests from the leftmost layers, which correspond to outer loops, then selects among TUs within the chosen layer in round-robin order, then selects streams within the chosen TU in configuration order, and finally selects requests within the chosen queue in FIFO order.
TUs within the same layer snoop their memory requests and upgrade the status of their \texttt{queued} elements if their address has been requested by another TU.

By default, memory requests within a stream are spawned \emph{eager}ly, meaning a cacheline can be requested as soon as an address for that cacheline is computed (\texttt{queued}). To reduce memory traffic, certain layers can adopt a \emph{lazy} loading strategy. Under lazy loading, a queued cacheline request is held while subsequent entries in the same queue continue to target the same cacheline; the request is issued only when the queue reaches an entry for a different cacheline or when the queue must make progress. This coalesces multiple entries that access the same cacheline into a single memory request, which is useful when a queue produces data more slowly than the memory latency.

\subsection{TU Queue Sizing} \label{sec:tmu-queue-sizing} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Queue storage is provisioned from shared per-lane storage at configuration time. Although TUs expose queues of fixed width internally, different logical layers require different depths: outer layers mostly produce loop bounds, whereas inner layers issue most memory requests and merges. The TMU therefore allocates shorter queues to lightly used leftmost layers and deeper queues to heavily used rightmost layers, coalescing unused physical storage across TUs in the same lane. An analytical model sizes these queues using statically estimated fiber lengths and nonzero counts.

\subsection{System Integration} \label{sec:tmu-system-integration} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\noindent\textbf{Placement:} 
As shown in \Cref{fig:tmu-architecture-overview}, each DAE core in our DAE multicore system features a TMU and a compute core. The TMU traverses fibers by loading data from the LLC and marshals the data into the outQ, which is written into the compute core's private L2 cache. Data from fiber traversals is unlikely to be reused in private caches; therefore, the TMU bypasses the private L1 and L2 caches for traversal reads and issues them directly to the shared LLC. This avoids consuming the small number of private-cache MSHRs and instead uses the larger, banked miss-handling capacity available at the LLC, enabling higher memory-level parallelism for sparse traversal. Each outQ is core-private; therefore, injecting it into the L2 cache enables faster compute throughput.

\noindent\textbf{Memory subsystem integration:} 
Like prior general-purpose processor engines, the TMU operates with virtual addresses and uses the host core's address translation hardware (MMU)~\cite{yang2021isca, kocberber2013micro, jones2016sc, mukkara2018micro, yu2015micro}. In particular, it queries the L2 TLB. A hit returns the physical address directly; a TLB miss is handled by the existing page-table walker and stalls only the corresponding TMU memory request, while other independent TMU requests can continue to make progress. We assume the TMU shares the host core's L2 TLB, so TMU traversal accesses may compete for L2 TLB capacity similarly to ordinary core loads. If the translation results in a page fault, the TMU interrupts the core so the OS can handle the fault. Once the missing translation is available, the MMU signals the TMU to retry the memory access.

The TMU operates decoupled from the compute core by issuing coherent read-only traversal requests and writing the resulting outQ into the compute core's private L2 cache. The outQ is a core-private producer-consumer buffer: the TMU writes it and the compute core reads it, but no other DAE core observes or modifies it. Thus, the TMU does not introduce new shared read-write data across DAE cores beyond ordinary coherent cache behavior.

\noindent\textbf{Context switching and exceptions:}
TMU architectural state must be saved and restored when a thread is context-switched. When the OS deschedules a thread that uses the TMU, it quiesces the TMU, saves its context, and restores it when the thread is rescheduled. 
On exceptions or syscalls that return to the same thread without descheduling it, the OS does not need to save TMU state. If handling the event deschedules the thread, the normal context-switch path quiesces and saves the TMU before another thread uses it.
Quiescing the TMU requires bringing its dataflow queues to a restartable state. The TMU stops issuing new memory requests and rolls each stream back to the last position at which all dependent queue entries are valid, which can be identified by walking the stream dependencies backwards. Any outstanding requests beyond that restart point are discarded or replayed after restore; once the queues contain only valid restartable entries, the TMU context can be saved.
After quiescence, the minimum context state that needs to be saved is the initial TMU configuration (e.g., queue types and sizes, \texttt{beg} and \texttt{end} iteration boundaries), the head of each TU \texttt{ite} stream, and some control registers such as the base outQ address and current writing offset. The memory-mapped outQ is private per thread.
Fortunately, support for efficiently saving large state is already implemented in the Linux kernel via on-demand expansion of per-task context switch buffers. This is used by the new Intel Advanced Matrix eXtensions (AMX)~\cite{intel2023amx,nassif2022isscc}, which employ tile registers that already occupy 8KB in current implementations.

\section{Scientific Sparse Tensor Algebra Evaluation} \label{sec:tmu-scientific-evaluation} %%%%%%%%%%%%%%

\subsection{Scientific Evaluation Methodology} \label{sec:tmu-scientific-methodology} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\subsubsection{Simulation Infrastructure} \label{sec:tmu-simulation-infrastructure} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\input{tab_gem5}

We evaluate the resulting DAE processor using the gem5 v20.1.0.0 simulator~\cite{lowepower2020gem5}. The DAE multicore system consists of 8 DAE cores composed of a TMU and a Neoverse-N1-like out-of-order cores, three levels of cache, 4 HBM2e memory channels, and a mesh-based network-on-chip modeling the AMBA 5 CHI protocol. The simulated system runs Ubuntu 20.04 with Linux kernel 5.4.65. \Cref{tab:tmu-dae-system-specs} summarizes the architectural parameters.

\subsubsection{Workloads} \label{sec:tmu-scientific-workloads} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\input{tab_inputs}
We evaluate our DAE proposal on several sparse linear and tensor algebra kernels and real-world applications with different characteristics. We employ high-performance multi-threaded software baselines that we either generated with the well-known TACO compiler~\cite{kjolstad2017oopsla} or extracted from existing reference libraries~\cite{phipps2019software,liu2021sparta}.
We vectorized all baselines with Arm SVE and utilized vector gather and scatter instructions where appropriate.
In particular, we evaluate the following kernels from \Cref{tab:tmu-tensor-algebra-mapping}:
\begin{itemize}
    \item \textbf{SpMV CSR}~\cite{williams2007sc}: Software baseline from TACO vectorized with Arm SVE. The TMU implements inner-loop vectorization (P1).
    \item \textbf{SpMSpM CSR}~\cite{gao2023systematic}: Implements $Z=AA^T$. Software baseline from TACO vectorized with Arm SVE. The TMU implements inner-loop vectorization (P2).
    \item \textbf{SpKAdd DCSR}~\cite{hussain2022ipdps}: Software baseline from TACO (\textit{k}=8) vectorized with Arm SVE. To preserve domain characteristics, input matrices ($A^x$ with $x=1...k$) are generated by cyclically distributing rows of the original matrix ($A$) to each input matrix (i.e., \textit{i}-th row of input $A^x_i=A_{i*k+x}$).
    \item \textbf{MTTKRP COO}~\cite{phipps2019software}: Performs a Matricized COO Tensor Times Khatri-Rao Product with the permutation optimization proposed by Phipps et al.~\cite{phipps2019software}. The TMU implements parallelism at the mode (P1) and rank (P2) levels.
    \item \textbf{SpTC CSF}~\cite{liu2021sparta}: Performs a tensor contraction of two CSF tensors with the expressions evaluated by Liu et al.~\cite{liu2021sparta}. We evaluate the symbolic phase to limit simulation time.
\end{itemize}
Moreover, we evaluate the following real-world applications:
\begin{itemize}
    \item \textbf{PR}: Performs the PageRank algorithm as implemented in the GAP Benchmark suite~\cite{beamer2015arxiv} (Jacobi-style method), optimized with Arm SVE.
    \item \textbf{TC}: Counts the triangles in a graph as in the fused GraphBLAS version~\cite{brock2022github} based on masked SpMSpM~\cite{milakovic2022parallel}.
    \item \textbf{CP-ALS}~\cite{phipps2019software}: Performs a canonical polyadic decomposition of a COO tensor with an alternating least squares algorithm, from the GenTen framework~\cite{phipps2019software}.
\end{itemize}
We run these applications with the settings suggested by the authors.
\Cref{tab:tmu-scientific-inputs} describes the inputs we used for all linear and tensor algebra applications, from SuiteSparse~\cite{davis2011university} and FROSTT~\cite{smith2017frostt}, respectively.

\Cref{fig:tmu-scientific-speedups-vs-cpu} reports the performance speedups achieved by the proposed DAE processor against a traditional one over the software baselines detailed in \Cref{sec:tmu-scientific-methodology}. Overall, the proposed DAE system achieves geomean performance speedups of 3.58$\times$, 2.82$\times$, and 4.94$\times$ on memory-intensive (SpMV, PR, MTTKRP, CP-ALS), compute-intensive (SpMSpM), and merge-intensive (SpKAdd, TC, SpTC) workloads, respectively. \Cref{fig:tmu-scientific-cycle-breakdown} shows, for each evaluated workload and input, the normalized cycles spent (left y-axis) (i) committing at least one instruction, (ii) on frontend (fetch) stalls, or (iii) on backend (commit) stalls. On the right y-axis, we show average load-to-use latency as seen by the cores.

SpMV and PR exhibit similar performance regimes, with geomean speedups of 3.32$\times$ and 2.74$\times$, respectively. PR attains slightly lower performance since the weight update is not accelerated by the TMU. \Cref{fig:tmu-scientific-cycle-breakdown} shows that the offloading tensor traversal and merging to the TMU drastically reduces backend stalls, the main bottleneck of these memory-intensive workloads. In addition, we observe a sharp reduction in load-to-use latency, e.g., from 67 to 23 cycles for M1 in SpMV. A similar behavior can be observed on the memory-intensive tensor workloads (MTTKRP\_MP, MTTKRP\_CP, and CP-ALS), which obtain geomean speedups of 3.76$\times$, 4.01$\times$, and 2.88$\times$, respectively. Overall, we observe that the TMU effectively hides long-latency misses on memory-intensive workloads~\cite{esmailidokht2024micro}.

The proposed DAE system also achieves speedups from 1.58$\times$ to 6.18$\times$ on SpMSpM (2.82$\times$ geomean). SpMSpM is a compute-intensive workload, as shown by the large portion of committing cycles in \Cref{fig:tmu-scientific-cycle-breakdown}. However, the time spent on computation is input-dependent, i.e., matrices with a higher nnzs-per-row count perform more computation. For input matrices with a larger portion of committing cycles (i.e., M1 and M5), offloading tensor traversal and lookups to the TMU does not provide large performance speedups due to Amdahl's law, but it still reduces backend stalls to a minimum. In contrast, for matrices that have a lower portion of committing cycles (i.e., M3 and M4), it delivers 6.18$\times$ and 4.58$\times$ speedups, respectively.

On merge-intensive workloads such as SpKAdd, TC, and SpTC, the the DAE processor achieves speedups of 6.98$\times$, 4.56$\times$, and 3.79$\times$, respectively. SpKAdd presents significant speedups for two main reasons. First, the TMU enables parallel loading of all eight matrices in a dataflow manner, unlocking memory-level parallelism that significantly reduces backend stalls. Second, it offloads merging, almost eliminating frontend stalls and reducing committing cycles (4$\times$ reduction on M4), since the compute core has less work to do. TC relies heavily on merging, experiencing a large portion of frontend stalls and committing cycles. In this case, offloading merging to the TMU is again able to almost completely eliminate frontend stalls and drastically reduce the amount of merging work performed by the core, greatly reducing committing cycles. A similar behavior can be observed in SpTC. Overall, workloads that perform merging operations greatly benefit from the TMU's ability to co-iterate multiple fibers, merge them in place, and produce a SIMD-friendly outQ for the core to process.

\subsection{System Utilization} \label{sec:tmu-system-utilization} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\input{fig_rooflines}

To explain the improvements the TMU brings in terms of system utilization, we present Roofline models~\cite{williams2009roofline} in \Cref{fig:tmu-scientific-rooflines}. Roofline models relate operational intensity (x-axis), measured by the ratio of total floating-point operations to total data movement, and performance in giga-flops (y-axis). The diagonal line draws the peak memory bandwidth, while the horizontal line is the processor's peak performance.

\Cref{fig:tmu-scientific-roofline-geomean} shows the data points for the evaluated workloads with the geomean for all inputs, except TC (integer arithmetic) and SpTC (symbolic phase) that do not perform floating-point computation. As can be seen, baseline CPU-only implementations are unable to use a substantial amount of memory bandwidth, attaining poor system utilization and compute throughput. The DAE processor, instead, achieves performance close to the memory bandwidth roof, and SpMV is almost saturating peak bandwidth, achieving significantly higher compute throughput. SpMSpM is unable to use as much bandwidth as the other workloads due to its compute-intensive nature.

The rest of the Roofline models focus on SpMV, SpMSpM, and SpKAdd, showing data for all inputs. For SpMV (\Cref{fig:tmu-scientific-roofline-spmv}), which is memory-intensive, the baseline CPU-only version cannot use the available memory bandwidth because data dependencies on long-latency memory accesses quickly fill out-of-order core resources and stall execution~\cite{esmailidokht2024micro}. The dataflow design of the TMU unlocks additional memory-level parallelism for offloaded traversals, increasing memory bandwidth utilization by almost 4$\times$ and leading to much better system-level performance. A similar behavior can be observed in SpKAdd for the CPU-only baseline versions (\Cref{fig:tmu-scientific-roofline-spkadd}), where the additional pressure that merging puts on core resources leads to even lower performance. The TMU again enables near-peak bandwidth utilization, which, combined with its merging support, significantly boosts overall performance.

Finally, for SpMSpM we also plot three additional dashed ceilings (\Cref{fig:tmu-scientific-roofline-spmspm}). We compute these ceilings by processing synthetic matrices, each storing a fixed number of nonzeros per row ($n=\{1,8,64\}$) located at column indices $\{0 .. n-1\}$, to proxy performance under ideal spatio-temporal locality. The data points starting from the right correspond to inputs M5 and M1, respectively. These two matrices have higher nnzs-per-row values (see \Cref{tab:tmu-scientific-inputs}) and perform better on the CPU-only baseline than other inputs due to higher operational intensity. DAE executions improve performance and bandwidth utilization, but performance is constrained by the inherent \emph{nnzs per row} compute ceilings.

\begin{figure}
    \centering
    \includegraphics[width=.8\columnwidth]{img_read-to-write_plot-tilted.pdf}
    \caption[Read-to-write ratio of scientific workloads.]{Read-to-write ratio of the proposed DAE processor on the scientific workloads described in \Cref{sec:tmu-scientific-methodology}. For each outQ block, the ratio compares the time the compute core spends consuming and processing the block against the time the TMU spends producing it, averaged across blocks. Values below one indicate that the core consumes blocks faster than the TMU produces them, so traversal or merging remains the bottleneck; values above one indicate that the TMU produces blocks faster than the core consumes them, so computation becomes the bottleneck. SpMV, MTTKRP, and TC are TMU-limited, SpKAdd and SpTC are close to balanced, and SpMSpM, PR, and CP-ALS are core-limited. Thus, the read-to-write ratio exposes whether each workload needs more access-side throughput, more compute-side throughput, or a balanced DAE pipeline.}
    \label{fig:tmu-scientific-outq-read-write-ratio}
\end{figure}

The compute core and the TMU work in a decoupled pipelined manner. Therefore, we introduce the \textit{read-to-write ratio}, defined as the ratio between the time it takes the compute core to process (read) an outQ block and the time it takes the TMU to produce (write) it, averaged over all blocks. \Cref{fig:tmu-scientific-outq-read-write-ratio} shows this ratio for the evaluated workloads. A value below one implies the compute core is faster than the engine. We observe this behavior for TC, since merging is offloaded to the TMU, and for SpMV and MTTKRP, where computation is very regular due to the SIMD-friendly data layout produced by the TMU. SpKAdd and SpTC have ratios close to one, which indicates balanced execution. SpMSpM, PR, and CP-ALS have higher ratios due to more compute and less regular computation, indicating that the bottleneck is on the compute core side.

Our evaluation demonstrates that the TMU successfully accelerates tensor traversals and merging operations, thereby improving overall system utilization. Moreover, performing computation on the core enables additional flexibility to seamlessly express and accelerate workloads that implement kernel fusion (TC) and that require evaluating partial results (CP-ALS).

\subsection{Comparison with Prior Sparse Architectures} \label{sec:tmu-prior-sparse-architectures} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\begin{figure}
    \centering
    \includegraphics[width=.8\columnwidth]{img_imp_single_multi.pdf}
    \caption[TMU vs. other architectural solutions for accelerating scientific models.]{Comparison of the proposed TMU against representative prior access-side techniques on scientific sparse kernels. Bars report speedup over the same traditional CPU baseline and optimized software implementations used in \Cref{sec:tmu-scientific-methodology}. \emph{IMP} augments the baseline with the Indirect Memory Prefetcher~\cite{yu2015micro}; \emph{Single-Lane} augments each core with a single-lane TMU with the same storage as the full design, proxying scalar traversal engines from prior work; and \emph{TMU} uses the full multi-lane TMU configuration from \Cref{tab:tmu-dae-system-specs}. \emph{Single-Lane} improves over the baseline but remains below the full TMU, which reaches 3.32$\times$ and 2.82$\times$ geomean speedups on SpMV and SpMSpM, respectively. Thus, decoupled traversal helps even in scalar form, but multi-lane parallel data loading is necessary to approach the full performance potential.}
    \label{fig:tmu-scientific-speedups-vs-prior-architectures}
\end{figure}

The graph-oriented traversal engines we compare against are integrated into multicore systems and are primarily designed for graph analytics~\cite{yang2021isca, mukkara2018micro}. They feature architectures similar to a single TMU lane, but with fewer primitives (i.e., stream types) and no support for parallel data loading or merging, limiting their applicability to simple linear algebra kernels. Two prominent examples are HATS~\cite{mukkara2018micro} and SpZip~\cite{yang2021isca}: the former exploits locality in graph communities, and the latter implements de(compression) techniques. Both optimizations are orthogonal to TMU operation. Therefore, we evaluate a \emph{Single-Lane} TMU with the same storage as the multi-lane \emph{TMU} employed throughout the evaluation. \Cref{fig:tmu-scientific-speedups-vs-prior-architectures} shows that \emph{Single-Lane} achieves 1.59$\times$ and 1.50$\times$ geomean speedups on SpMV and SpMSpM, while \emph{TMU} achieves 3.32$\times$ and 2.82$\times$, respectively. This indicates that graph-oriented traversal engines would also benefit from parallel data loading.

We also evaluate the Indirect Memory Prefetcher (IMP)~\cite{yu2015micro}, configured as recommended by the paper's authors, including the use of virtual addresses to prefetch across memory page boundaries. IMP performs well on SpMV, with an average speedup of 1.25$\times$, but fails to deliver performance improvements on SpMSpM due to thrashing of partial results. Overall, \emph{Single-Lane} and \emph{TMU} obtain better performance because they unlock more MLP while always fetching useful data.

\subsection{RTL Implementation and Area Analysis} \label{sec:tmu-rtl-area-analysis} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
We implement the TMU in System Verilog using the parameters listed in \Cref{tab:tmu-dae-system-specs} and synthesize the design using the GlobalFoundries 22nm FD-SOI technology node. We have used the Cadence Genus tool v19.11 for the logical synthesis and the Cadence Innovus tool v19.11 for the place-and-route.
The standard cell libraries have 8-tracks, low Vt, and a 104 CPP. We have used high-performance dual-port SRAMs to implement the different data and metadata arrays inside the engine. 
The area cost of the TMU is $0.0704$mm$^2$, where each lane occupies just $0.0080$mm$^2$. The TMU requires 1.52\% of the area of a Neoverse N1 core~\cite{pellegrini2020arm}, the core modeled in our evaluation, when scaled to the same technology node~\cite{stillmaker2017scaling}.
Moreover, the entire sparse engine is $0.5\times$ smaller than a 32 KB, 8-way L1 data cache in 22nm technology.

As with irregular memory accesses in scientific workloads, offloading embedding lookups to the TMU has several advantages. Because the TMU implements tensor traversal and loading with specialized dataflow hardware, it can issue memory requests with higher throughput and efficiency than the core. Moreover, because the TMU can run at a lower frequency, it can track 8$\times$ more outstanding requests without timing issues and with low overhead (as discussed in \Cref{sec:tmu-rtl-area-analysis}). \Cref{fig:tmu-gnn-bandwidth-vs-miss-rate} demonstrates that the TMU can track 82\% of the outstanding memory requests required to achieve full throughput (one request per cycle), whereas the CPU can track only 16\%.

This additional memory-level parallelism translates directly into throughput and energy efficiency. As shown in \Cref{fig:tmu-gnn-request-throughput-power} and \Cref{fig:tmu-gnn-request-efficiency-improvement}, the TMU achieves 5.7$\times$ higher requests/s and 5.6$\times$ higher requests/s/W than traditional cores. It also outperforms a core with doubled outstanding-request resources by 5.2$\times$ in requests/s and 6.3$\times$ in requests/s/W (\Cref{fig:implications-cpu-mlp-scaling-cost}).

Finally, these per-core improvements scale to system-level bandwidth utilization. As shown in \Cref{fig:tmu-gnn-hbm-bandwidth-improvement}, the TMU uses 4$\times$---8$\times$ more memory bandwidth than a traditional core. Consequently, \Cref{fig:tmu-gnn-bandwidth-scaling} shows that DAE architectures (1)~achieve higher performance with the same core count, and (2)~require fewer cores to achieve the same performance, improving efficiency.

\subsection{Specialized TMU-Enabled DAE Architectures} \label{sec:specialized-tmu-enabled-dae-architectures} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Once embedding lookup is decoupled from computation, the compute side no longer needs to be a large out-of-order core for every workload. Building on the embedding evaluation in \Cref{sec:tmu-embedding-evaluation}, this section explores how the same decoupling principle enables more specialized architectures tailored for embedding operations.

The DAE processor described in \Cref{sec:tmu-embedding-methodology} is based on a conventional multicore design, augmented with a TMU per core to offload embedding lookups. While this approach improves performance and efficiency with minimal architectural changes, it does not fully exploit the specialization opportunities enabled by the TMU.

As shown in \Cref{fig:tmu-specialized-power-breakdown}, more than 75\% of the processor power is consumed by compute cores and associative caches. However, these components are overprovisioned for embedding workloads, where computation is limited to simple vector accumulation. Furthermore, as discussed in \Cref{sec:embedding-workload-characterization}, cache effectiveness depends strongly on input reuse. Consequently, both compute and cache resources can be significantly underutilized, as illustrated in \Cref{fig:tmu-specialized-cache-compute-utilization}.

Motivated by these observations, in this section we explore two complementary optimizations: (i)~reducing the complexity of DAE compute cores to improve energy efficiency, and (ii)~moving these simplified cores closer to memory to bypass the cache hierarchy.

The \texttt{dae-lm} system includes six PN-HBM devices, each treated as an accelerator with a private address space. \Cref{fig:tmu-specialized-dae-performance-efficiency} summarizes the performance and efficiency impact of the proposed optimizations. Overall, reducing compute core complexity (\texttt{dae-lh}) substantially improves energy efficiency with minimal performance degradation, while near-memory execution (\texttt{dae-lm}) provides additional gains for low-reuse workloads.

The \texttt{dae-lh} configuration achieves 94\%–99\% of the performance of \texttt{dae-bh}, while improving performance per watt by 2.66$\times$–4.12$\times$. This is because, as demonstrated earlier, embedding operations underutilize large out-of-order cores, and simpler cores can deliver comparable throughput at only 10\%–12\% of the energy. Workloads with higher node degree achieve better performance due to increased computation per memory access, while low-reuse workloads exhibit lower efficiency due to dominant memory and cache overheads.

In contrast, \texttt{dae-lm} provides the highest benefits for low-reuse datasets, where caches provide limited filtering. By moving DAE cores closer to memory, this configuration eliminates unnecessary cache accesses, reducing both latency and energy. For example, on \texttt{products}, \texttt{dae-lm} achieves 1.85$\times$ higher performance and 4.39$\times$ higher efficiency than \texttt{dae-lh}, and 1.79$\times$ higher performance and 7.86$\times$ higher efficiency than \texttt{dae-bh}. Similar trends are observed for \texttt{mag}, where \texttt{dae-lm} improves performance by 9\% and efficiency by 83\% over \texttt{dae-lh}.

These gains stem from eliminating cache overheads, which account for up to 50\% of total energy in low-reuse workloads. However, for higher-reuse workloads, caches remain beneficial. For example, on \texttt{arxiv}, \texttt{dae-lm} is slightly slower (1\%) but 1.46$\times$ more efficient than \texttt{dae-lh}. On \texttt{proteins}, where most accesses are cacheable, \texttt{dae-lm} is both slower and less efficient due to increased memory traffic. In this case, \texttt{dae-lh} achieves 21\% higher performance and slightly better efficiency.

Overall, \texttt{dae-lh} is preferable for high-reuse workloads, while \texttt{dae-lm} is better suited for low-reuse workloads.

\section{Summary} \label{sec:tmu-summary}

This chapter introduced the TMU, a near-core access unit that maps sparse tensor traversal, coordinate merging, and data marshaling to specialized hardware while preserving CPU vector execution for arithmetic. Across scientific sparse tensor algebra workloads, the TMU improves performance by exposing memory-level parallelism, reducing merge overheads, and producing SIMD-friendly operand streams at low area cost. Across machine learning embedding operations, the TMU improves bandwidth utilization and performance per watt, and the same decoupling principle enables more specialized DAE organizations with simpler or near-memory compute cores. The cost of this flexibility is a more complex programming model: users or compilers must describe tensor traversal, merging, callbacks, and outQ construction. \Cref{sec:dae-compilation} introduces Ember, a compiler stack that automates this mapping.

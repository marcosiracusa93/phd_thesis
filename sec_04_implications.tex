\chapter{Architectural Implications of Sparse Tensor Workloads} \label{sec:architectural-implications}

This chapter identifies the architectural requirements imposed by sparsity. \Cref{sec:sparse-scientific-computing} studies sparse scientific workloads and shows that compressed traversal and coordinate merging expose irregular memory accesses and data-dependent control flow that prevent conventional processors from using their available compute and memory bandwidth. \Cref{sec:ml-embedding-workloads} then studies sparse machine learning workloads, where embedding operations generate indirect vector lookups with widely varying spatial and temporal locality. Together, these results motivate the TMU--CPU system introduced in \Cref{sec:tmu}: a design that decouples sparse traversal, merging, and marshaling from vector computation.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Sparse Scientific Computing} \label{sec:sparse-scientific-computing} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

We study sparsity in scientific computing by analyzing three proxy kernels, each chosen to isolate a distinct architectural stressor:
\begin{itemize}
    \item \emph{Sparse Matrix--Vector Multiplication} (SpMV)~\cite{williams2007sc}, which multiplies a CSR matrix and a dense vector and outputs a dense vector ($Z_i = A_{ij} B_j$). Since co-iteration of $A_{*j}$ and $B_j$ is generally implemented as a memory-intensive scan-and-lookup operation (\Cref{sec:scan-and-lookup}), we use SpMV as a proxy for sparse traversal and indirect scalar lookup.
    \item \emph{Gustavson's Sparse Matrix--Sparse Matrix Multiplication} (SpMSpM)~\cite{gao2023systematic}, which multiplies and outputs CSR matrices ($Z_{ij} = A_{ik} B_{kj}$ with $(ikj)$ schedule). SpMSpM performs the same scan-and-lookup operation as SpMV but, instead of scalars, it looks up and loads whole rows of $B$, which are then reduced into a single row. For this reason, SpMSpM is a proxy for scan-and-lookup operations with higher spatial locality, as well as for the accumulation of intermediate results.
    \item \emph{Sparse Matrix Addition} (SpAdd)~\cite{hussain2022ipdps}, which adds and outputs CSR matrices ($Z_{ij} = A_{ij} + B_{ij}$) by repeatedly co-iterating and joining (disjunctive merge) matrix fibers with the same row index $i$. Therefore, SpAdd is representative of coordinate merging and the data-dependent control flow it induces.
\end{itemize}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Scientific Workload Methodology} \label{sec:scientific-workload-methodology} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

We profile high-performance implementations of these kernels---from the Kokkos library~\cite{edwards2014kokkos}---both on an HPC processor, the Fujitsu A64FX~\cite{sato2020design}, and on a data-center processor, the AWS Graviton 3. While the A64FX has more memory bandwidth per core (1~TB/s for 48 cores vs.\ 300~GB/s for 64 cores), Graviton 3 has cores with more out-of-order resources and larger caches. To understand the implications of these architectural choices across domains, we test these kernels on the largest 1000 matrices drawn from different domains in the SuiteSparse Matrix Collection~\cite{davis2011university}.

\Cref{fig:roofline_sparse} presents the Roofline models of these kernels and matrices running on the two evaluated processors. First, we observe that sparse scientific kernels from different domains exhibit widely varying operational intensities. This variation stems from differences in temporal locality, which directly affect data reuse and memory access patterns. More clustered domains exhibit higher reuse and better cache utilization, reducing the amount of data fetched from memory per operation and therefore increasing operational intensity. This behavior is particularly evident for kernels such as SpMSpM, which accumulate partial results in cache. Nevertheless, a common trend across all kernels is that, although performance generally scales with operational intensity, (1)~the average memory bandwidth utilization of the two processors is substantially different and (2)~memory bandwidth utilization for each processor exhibits significant variability across kernels and matrices.

These trends are even more apparent in \Cref{fig:utilization_sparse}, which reports compute and memory bandwidth utilization for both processors. Minimum, maximum, and average values are summarized in \Cref{tab:utilization}. We focus primarily on memory bandwidth, which is the dominant bottleneck. Overall, most kernels and matrices utilize only a small fraction of the available memory bandwidth, although the Graviton~3 achieves utilization levels up to an order of magnitude higher than the A64FX. Furthermore, bandwidth utilization for a given kernel and processor can vary by several orders of magnitude depending on the input matrix.

To better understand the source of these inefficiencies, we measure the fraction of frontend and backend stalls on each processor, reported in \Cref{fig:stalls} and summarized in \Cref{tab:stalls}. Frontend stalls arise from inefficiencies in the instruction pipeline, whereas backend stalls originate from inefficiencies in the compute units and memory subsystem. For sparse kernels, frontend stalls are primarily caused by branch mispredictions in data-dependent loop branches, while backend stalls are largely due to irregular memory accesses~\cite{dongarra2013metric,dongarra2013hpcg,talati2021hpca,talati2022isca}. Therefore, bandwidth utilization is not determined by reuse alone: even when locality reduces backend pressure, data-dependent branches can stall the frontend and limit how effectively the core generates and sustains memory requests, generating high variability in memory bandwidth utilization. More specifically, we observe that:
\begin{itemize}
    \item For SpMV, unlike the Graviton~3, the A64FX exhibits substantially more backend stalls than frontend stalls. We attribute this behavior to the A64FX being primarily optimized for regular high-throughput computation and therefore being less resilient to irregular memory accesses. Its relatively small cores provide limited instruction-level and memory-level parallelism for tolerating long memory latencies~\cite{esmailidokht2024micro}. In contrast, the Graviton~3 exhibits a larger fraction of frontend stalls, likely because its more aggressive cores sustain higher memory-level parallelism while incurring higher branch misprediction penalties.
    
    \item For SpMSpM, the A64FX achieves better backend utilization than in SpMV. Conversely, on the Graviton~3, SpMSpM exhibits backend utilization comparable to SpMV. These results suggest that (i)~scan-and-lookup operations with higher spatial locality benefit significantly from high-bandwidth architectures, and (ii)~reduction operations do not severely impact backend utilization because partial results typically fit in cache~\cite{nagasaka2018high}. However, computing these reductions benefits from stronger frontend capabilities and more aggressive speculation, such as those provided by the Graviton~3 cores.
    
    \item For SpAdd, the frontend becomes the dominant bottleneck due to highly data-dependent branching behavior, particularly on cores with limited out-of-order execution capabilities such as those in the A64FX~\cite{hussain2022ipdps}.
\end{itemize}

Overall, these results indicate that (i)~modern general-purpose processors typically provide sufficient compute throughput for the operational intensity of sparse algebra workloads, and (ii)~existing cache hierarchies can effectively exploit locality in certain domains and algorithms by capturing graph communities and storing partial results. However, (i)~data-dependent control flow arising from fiber traversal and merging~\cite{talati2022isca} and (ii)~irregular memory accesses generated by scan-and-lookup operations~\cite{talati2021hpca} fundamentally limit processor utilization, resulting in performance that reaches only a small fraction of the available peak throughput~\cite{dongarra2013metric,dongarra2013hpcg}. These observations suggest that sparse tensor architectures should not simply add more compute throughput. Instead, they should remove traversal and merge control from the main pipeline, expose enough memory-level parallelism for irregular accesses, and feed conventional compute units with dense values once the sparse structure has been resolved.

As discussed in \Cref{sec:sparsity-in-machine-learning}, embedding operations are also dominated by irregular lookup operations. However, in addition to varying in temporal locality, they can also vary substantially in spatial locality, since embedding vectors can range from tens to hundreds of elements. For this reason, we use embedding operations to study the architectural implications of irregular memory accesses with different spatial and temporal locality characteristics. \Cref{sec:embedding-workload-methodology} first describes the workloads, inputs, and experimental setup. \Cref{sec:embedding-workload-characterization} then characterizes embedding operations from different machine learning models, and \Cref{sec:embedding-performance-gpus,sec:embedding-performance-cpus} analyze their performance on traditional architectures. Finally, \Cref{sec:ideal-mlp-requirements,sec:cost-of-scaling-mlp} quantify the scaling limitations of traditional architectures and the need for alternative solutions.

\subsection{Embedding Workload Characterization} \label{sec:embedding-workload-characterization} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\input{tab_characterization_split}

\Cref{tab:characterization-code} characterizes the code of embedding operations across various machine learning models, whereas \Cref{tab:characterization-embedding} characterizes their memory requirements. For each model, we first analyze its loop hierarchy (column~1 in \Cref{tab:characterization-code}) and compute-per-lookup ratio (column~2 in \Cref{tab:characterization-code}), which approximate compute requirements. Then, we compute the memory footprint of the embedding tables to understand their storage demands (column~1 in \Cref{tab:characterization-embedding}). Finally, we characterize their spatio-temporal locality to gauge the effectiveness of caches and prefetchers for embedding lookups (columns~2 and 3 in \Cref{tab:characterization-embedding}).

We characterize temporal locality through the concept of \emph{reuse distance}---the number of other vectors accessed before a vector is accessed again~\cite{ding2003pldi}. If a cache can hold $x$ vectors, an access with reuse distance greater than $x$ will likely result in eviction. For a given input, we first construct a histogram of all reuse distances, which we then integrate and normalize to obtain the Cumulative Distribution Function ($CDF$). Hence, $CDF(x)$ approximates the hit probability for a cache that can hold $x$ vectors. Spatial locality, instead, is characterized by the size of the embedding vector. In \Cref{sec:ideal-mlp-requirements} we use spatial and temporal locality to estimate the ideal memory-level parallelism required to run at peak throughput.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsubsection{Graph Learning Models} \label{sec:embedding-characterization-graph-learning} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

As SpMM operations in GNNs perform one multiplication and one element-wise addition per embedding lookup, they exhibit a compute-per-lookup ratio of 2 (column~2 in \Cref{tab:characterization-code}). Message Passing (MP), implemented as an SDDMM operation fused with SpMM, incurs a higher compute-per-lookup ratio. Knowledge Graph workloads (KGs) show the lowest ratio. Overall, across these applications the compute-per-lookup ratio never exceeds 2.5—strikingly low for traditional architectures optimized for dense tensor algebra. This limitation is compounded by the wide variation in spatio-temporal locality across workloads and inputs: some embedding lookups can be filtered by caches, whereas others must fetch data directly from memory, making locality a dominant factor in performance.

The CDF (column~2 in \Cref{tab:characterization-embedding}) captures temporal locality and cache utilization. For example, at a reuse distance of 1K, GNNs have a CDF below 20\%. In other words, more than 80\% of embedding lookups touch over 1K distinct vectors before reaccessing the same one, leaving minimal caching opportunity for these inputs. KGs exhibit even lower temporal locality, while MP depends heavily on the input graph structure and can expose substantially different cache behavior across inputs.

Spatial locality is similarly limited (column~3 in \Cref{tab:characterization-embedding}). GNN layers access between 8 and 349 embedding elements per lookup, MP accesses 128, and KGs reach the highest value at 512. Even these upper bounds remain modest for conventional prefetching mechanisms.

Finally, all three workloads require architectures with memory capacity in the tens of gigabytes to store their embedding tables (column~1 in \Cref{tab:characterization-embedding}). Such capacities make off-chip memory capacity a first-order architectural constraint for current machine learning accelerators~\cite{nvidia2024h100,jouppi2023isca}.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsubsection{Deep Learning Recommendation Models} \label{sec:embedding-characterization-dlrms}  %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

As EB functions perform one element-wise sum per embedding lookup, they have a compute-per-lookup ratio of 1 (column~2 in \Cref{tab:characterization-code}). Overall, DLRMs invoke the EB function tens to thousands of times to aggregate all categorical features in a batch~\cite{ibrahim2022memsys,gupta2020isca}. Each invocation aggregates tens to hundreds of embedding vectors from a single table with millions of entries~\cite{ibrahim2022memsys}, each vector storing 32--256 elements (column~3 in \Cref{tab:characterization-embedding}). While this necessitates a large memory footprint (column~1 in \Cref{tab:characterization-embedding}), embedding vectors are accessed with some degree of reuse~\cite{sethi2022asplos,ginart2021isit,joglekar2020neural,acun2021hpca,wang2022sc}, and modern caches can filter a significant fraction of embedding accesses~\cite{ibrahim2022memsys}.

If we assume embedding vectors with 256 FP32 elements, a 1~MB cache can fit 1K vectors. Given the CDF of a real-world input such as the Criteo 1TB dataset~\cite{criteo2024dataset} (column~2 in \Cref{tab:characterization-embedding}), \texttt{CDF\_ftr0}(1K) = 63\%, whereas \texttt{CDF\_ftr2}(1K) = 99\%, which approximates the cache hit probability. Similarly, a 2~MB cache would filter 65--99\% of the total accesses. Hence, while caches are essential for DLRMs, they provide diminishing returns. Moreover, given the relatively small embedding size, prefetchers yield limited benefits.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsubsection{Sparse Attention in Language Models} \label{sec:embedding-characterization-llms} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Sparse attention mechanisms replicate blocks of embeddings from the key tensor into the query tensor. As shown in \Cref{tab:characterization-embedding}, the larger the block, the higher the spatio-temporal locality over keys (higher horizontal CDF segment). However, smaller blocks reduce the required compute. Thus, larger blocks enable better system utilization on compute-oriented machines, while smaller blocks enable lower inference latency on machines with more efficient memory subsystems.

Taken together, these workloads require architectures that tolerate wide variation in spatial and temporal locality. They must exploit cache reuse when it exists, but also sustain many low-reuse vector lookups without depending on dense arithmetic intensity to hide memory latency.

\Cref{fig:gpu-benchmark-runtime} shows the runtime breakdown of these models running on GPUs, which are the most widely used accelerators for machine learning applications. Embedding operations consume the majority of cycles, especially in GNNs and DLRMs. Because both GNNs and DLRMs must pool the embedding vectors of each neighbor, their embedding runtime scales roughly with the average number of neighbors (i.e., vertices per edge).

The second most critical operation is matrix multiplication, particularly in LLMs and DLRMs. While DLRMs and GNNs have similar embedding operations, DLRMs include more matrix multiplication layers, which account for more than 20\% of total cycles. In addition, DLRMs compute interactions among all pooled sparse features and dense features, further increasing their compute requirements. Consequently, after embedding operations, matrix multiplications are also a key component to consider when designing efficient architectures for these models.

Finally, elementwise vector and scalar operations are most relevant for KGs, which rely on elementwise operations to compute norms. It is also worth noting that high-performance GPU implementations spend a sizable fraction of time in ``other'' operations, such as input sorting and related preprocessing.

\Cref{fig:gpu-benchmark-roofline} shows the Roofline model~\cite{williams2009roofline} for embedding operations. Overall, although these operations are critical, they achieve less than 30\% of peak compute utilization. As reported in \Cref{tab:characterization-embedding}, GNNs and KGs exhibit the lowest temporal locality and therefore the highest memory bandwidth utilization---yet even in these cases, bandwidth utilization remains below 55\%.

Unlike typical machine learning operations (e.g., dense matrix multiplication), embedding operations involve looking up embedding vectors from scattered memory locations and aggregating them with element-wise operations. GPUs, however, are designed for massively parallel and regular computation where (1)~memory accesses can be coalesced and (2)~there is sufficient computation to hide memory latency. In embedding workloads, (1)~embedding vectors are only hundreds of elements long, limiting coalescing opportunities, and (2)~element-wise operations do not provide enough computation to hide memory latency, resulting in low GPU utilization~\cite{pellauer2023symphony}.

Combined with the high cost of GPUs and their limited memory capacity for storing large embedding tables, these inefficiencies make GPUs a poor target for embedding operations. Efficient support for these models must therefore be close to large memories and cannot rely solely on GPU-style coalescing or dense computation to hide lookup latency. To address this issue, several production systems offload embedding operations to CPUs while keeping dense neural network layers on GPUs~\cite{chen2023icde}, or execute the entire pipeline on CPUs~\cite{mudigere2022isca}. Although CPUs offer a more cost-effective alternative, commodity processors remain poorly optimized for the highly irregular memory accesses generated by embedding lookups, as demonstrated next, leaving substantial performance untapped.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Embedding Performance on Off-the-Shelf CPUs} \label{sec:embedding-performance-cpus} %%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\Cref{sec:embedding-performance-cpus,sec:ideal-mlp-requirements,sec:cost-of-scaling-mlp} present a comprehensive quantitative study of graph learning models on off-the-shelf CPUs, highlighting their main limitations and optimization opportunities. Given the diverse spatio-temporal locality characteristics of the models we analyze, we expect these findings to generalize to the other workloads listed in \Cref{tab:characterization-embedding}.

\input{fig_misses}

Overall, CPU cores are designed to access data primarily from local caches, which are populated by hardware prefetchers. However, these mechanisms are often ineffective for irregular embedding lookups, especially when reuse is low~\cite{gupta2020hpca}. \Cref{fig:misses} shows that graphs from different domains exhibit substantially different spatio-temporal locality characteristics, leading to markedly different cache behaviors. More clustered graphs, which reuse embedding vectors more frequently, achieve significantly better cache utilization. In contrast, sparser graphs experience consistently high miss rates across the entire cache hierarchy. Furthermore, larger embedding vectors improve L1 cache behavior due to increased prefetching opportunities, but degrade performance at lower cache levels because of higher cache contention and eviction pressure. Overall, GNN layers experience L3 miss rates ranging from 38\% to 92\%, resulting in a substantial number of accesses to HBM memory.

\input{fig_embedding_implications_split}

As a result, embedding lookups generate a high volume of long-latency memory requests~\cite{esmailidokht2024micro}. For instance, as shown in \Cref{fig:ltu-gnn}, up to 86\% of the memory requests in GNN embedding operations take more than $10\times$ the latency of an L1D cache access, and up to 36\% exceed $100\times$ that latency because they must reach HBM.

When a core issues a memory request, it must allocate entries in the Reorder Buffer (ROB), Load--Store Queue (LSQ), and Miss-Status Handling Registers (MSHRs) at each cache level. The longer the memory access, the more entries are required to sustain multiple outstanding requests, a property generally known as memory-level parallelism. However, as these structures do not scale easily, traditional architectures provision just enough capacity to efficiently load data from local caches, not from HBM. As shown in \Cref{fig:embedding-implications}, off-the-shelf CPU cores achieve low request throughput across all inputs because long-latency embedding lookups require more memory-level parallelism than the core can sustainably provide~\cite{esmailidokht2024micro}, and because data-dependent traversal introduces additional control overhead. This results in low HBM utilization even for inputs whose requests mostly miss the caches and reach memory. Therefore, an efficient architecture for embedding operations must expose high memory-level parallelism without tying every in-flight vector lookup to scarce out-of-order core resources.

\Cref{fig:mlp-model} illustrates the system abstraction underlying our model. In \Cref{fig:mlp-system-abstraction}, the system has $N$ logical levels, where $L_0$ is the core, $L_1 \ldots L_{N-2}$ are the caches, and $L_{N-1}$ is HBM. The latency to access $L_b$ from $L_a$ is $L_{L_a \rightarrow L_b}$ clock cycles. Each level sends out memory requests for the next level at a throughput $T_x$.

We compute the number of outstanding memory requests using Little's rule~\cite{little1961proof}, which states that, assuming the core issues memory requests at throughput $T_0$, the number of outstanding requests at each level is:
\begin{equation}
\label{eq:little-rule}
R_x = T_x \times \overline{L_{L_x}}
\end{equation}
where both terms depend on the cache hit rate per level. Intuitively, the longer the memory requests or the higher the throughput, the higher the number of outstanding memory requests.

We define the cache hit or miss probability at levels $x$ and $y$ as $P_{L_x^{a_x} L_y^{a_y}}$, with $a_x, a_y \in \{\text{h}, \text{m}\} = \{\text{hit}, \text{miss}\}$. Moreover, we define the (conditional) probability of a hit or miss at level $x$ given a hit or miss at level $y$ as
\begin{equation}
P_{L_x^{a_x} | L_y^{a_y}} = P_{L_x^{a_x} L_y^{a_y}} / P_{L_y^{a_y}}.
\end{equation}
Hence, the \emph{output throughput} $T_x$ at level $x$ is 
\begin{equation}
T_x = T_{x-1} \times P_{L_x^{m} | L_1^{m} \ldots L_{x-1}^{m}} \;\text{cycle}^{-1},
\end{equation}
with $T_0$ the throughput at which the core issues memory requests.
Similarly, the \emph{average request latency} $\overline{L_{L_x}}$ at level $x$ is
\begin{equation}
\overline{L_{L_x}} = 
\sum_{l = x+1}^{N-1}
L_{L_x \rightarrow L_l} \times
P_{L_{x+1}^{m} \ldots L_{l-1}^{m} L_l^{h} | L_1^{m} \ldots L_x^{m}} \;\text{cycles}.
\end{equation}
We compute these probabilities from the spatio-temporal locality of the input model.

As discussed in \Cref{sec:embedding-workload-characterization}, we model spatial locality via the embedding vector size, and temporal locality via the CDF of the reuse distance~\cite{ding2003pldi}. Recall that the reuse distance is the number of other embedding vectors accessed before a vector is accessed again. If a cache can hold $x$ vectors, an access with reuse distance greater than $x$ will likely result in eviction. Hence, we can model the hit or miss probability of a given cache as the fraction of accesses with reuse distance smaller or greater than $x$. We model such probabilities by first constructing a histogram of all reuse distances, which we then integrate and normalize to obtain the CDF. Thus, $CDF(x)$ approximates the hit probability of that cache, and \Cref{fig:mlp-reuse-cdf} shows how to derive the above probabilities starting from the CDF. \Cref{fig:cdf-gnn} characterizes the graphs in \Cref{tab:graph-inputs}; its ordering across inputs matches the measured cache behavior in \Cref{fig:misses}, suggesting that reuse-distance CDFs are a promising predictor of cache performance. We now validate this connection directly against gem5.

We model \emph{inference latency} from the throughput $T^i_l$ and number of outstanding requests $R^i_l$ per level $l$, where the superscript $i$ indicates \emph{ideal}. We start by computing the \emph{ideal inference latency} while running at full core throughput (one load per cycle per port):
\begin{equation}
L^i = \left\lceil \frac{\text{numLookups} \times \text{numLoadsPerLookup}}{\text{numReadPorts}} \right\rceil
\end{equation}
where \texttt{numLookups} is the number of loaded embedding vectors, \texttt{numLoadsPerLookup} is the number of vector loads required to fetch an embedding vector, and \texttt{numReadPorts} is the number of read ports out of the core. Given a system where each component at level $l$ has:
\begin{itemize}
    \item \emph{max throughput} $T^m_l$ (bounded by its ports and frequency),
    \item \emph{max number of requests} $R^m_l$ (bounded by MSHRs),
\end{itemize}
where the superscript $m$ indicates \emph{maximum}, we define the fraction of ideal execution that each component at level $l$ can sustain as:
\begin{equation}
S^{t}_l = \min \left( 1, \frac{T^m_l}{T^i_l} \right)
\end{equation}
for throughput, and
\begin{equation}
S^{r}_l = \min \left( 1, \frac{R^m_l}{R^i_l} \right)
\end{equation}
for request tracking capacity. These scaling factors are 1 when the corresponding resource can sustain ideal execution and smaller than 1 when it becomes a bottleneck. We then compute the limiting scaling factor $S$ as:
\begin{equation}
S = \min \left( \min_l S^{t}_l, \min_l S^{r}_l \right).
\end{equation}
Finally, we compute the \emph{actual latency} $L^a$ by rescaling the ideal latency $L^i$ according to the limiting factor:
\begin{equation}
L^a = \frac{L^i}{S}.
\end{equation}

Increasing the memory-level parallelism of a CPU core to track more in-flight requests requires scaling up the reorder buffer, load-store queue, and miss-status handling registers~\cite{sgherzi2024jpdc}. However, these resources scale inefficiently. As shown in \Cref{fig:dse-cpu}, for datasets with high reuse, doubling them improves performance by only 12\% while increasing power consumption by 25\%, whereas for datasets with low reuse, it improves performance by 3\% while increasing power consumption by 18\%. Besides degrading performance per watt, scaling up these resources introduces timing closure challenges~\cite{siracusa2022tc}, which would require lowering the core's frequency and, consequently, overall performance.

A common solution is to scale out the number of cores. However, this is also ineffective. As shown in column~4 in \Cref{fig:embedding-implications}, we would need 43---72 traditional CPU cores to saturate a single HBM stack, depending on the input reuse. Hence, we would need an unfeasible amount of cores to saturate the large memory bandwidth of current architectures. Therefore, traditional architectures cannot scale to that level of memory-level parallelism. These results point to the same design principle as the scientific workloads: sparse accesses should be decoupled from the compute pipeline so that memory-level parallelism can scale without proportionally scaling expensive core structures.

\section{Summary} \label{sec:architectural-implications-summary}

In this chapter, we have demonstrated that traditional architectures that tightly couple control flow, memory access, and computation are fundamentally inadequate for sparse tensor algebra workloads. Scientific kernels show that traversal, scan-and-lookup operations, and coordinate merging leave both compute units and memory bandwidth underutilized. Machine learning embedding operations show a complementary bottleneck: they require many long-latency vector lookups whose locality varies widely across models and inputs~\cite{esmailidokht2024micro}. Scaling conventional cores up or out does not provide this memory-level parallelism efficiently. In \Cref{sec:tmu}, we demonstrate how decoupling sparse traversal, merging, and marshaling from vector computation can overcome these limitations and substantially improve performance and efficiency.

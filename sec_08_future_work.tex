\chapter{Future Work} \label{sec:future-work}

The TMU and Ember demonstrate that DAE execution can make sparse tensor workloads both more efficient and more programmable. This chapter broadens workload and system characterization (\Cref{sec:future-work-workload-system-characterization}) and advances TMU implementation and system integration (\Cref{sec:future-work-tmu-implementation-integration}). It then extends the TMU architecture (\Cref{sec:future-work-extending-tmu}) and expands Ember toward full sparse tensor algebra (\Cref{sec:future-work-extending-ember}).

\section{Broader Workload and System Characterization} \label{sec:future-work-workload-system-characterization}

\begin{itemize}
    \item A natural extension of the characterization and modeling effort in \Cref{sec:architectural-implications} is to broaden the set of evaluated workloads, input datasets, and target architectures. This includes additional scientific kernels, emerging machine learning models, training workloads, distributed executions, and systems with different memory hierarchies. Such a study would help distinguish which bottlenecks are fundamental consequences of sparsity from those that are specific to the workloads and machines evaluated in this thesis, and would provide stronger guidance for future DAE designs.
\end{itemize}

\section{TMU Implementation and System Integration} \label{sec:future-work-tmu-implementation-integration}

\begin{itemize}
    \item A near-term direction is to continue extending and optimizing the RTL implementation of the TMU. Xicu Marí Prats's master's thesis implemented the first scalar TMU prototype, consisting of one Traversal Unit (TU), one layer, and one lane~\cite{mariprats2025mastersthesis}. Since then, we have extended the design with multiple layers, enabling nested-loop traversal, and multiple lanes, enabling sparse coordinate merging. The next step is to use the multi-lane design for vectorization and to integrate the TMU with a vectorized core. This path would progressively close the gap between the initial scalar prototype and the multi-layer, multi-lane TMU evaluated in \Cref{sec:tmu}.

    \item A complementary direction is to continue improving the integration of the TMU into real systems-on-chip. This line of work follows Diego Gorfini's master's thesis, which builds on the first TMU SoC prototype by improving the interface between the TMU, the core, Cohort, and OpenPiton~\cite{mariprats2026bscsymposium}. The current design uses coherent shared-memory queues for core-TMU communication, avoiding memory-mapped I/O and ISA extensions, and explores a hybrid tile organization that co-locates the TMU, Cohort, and the core to reduce inter-tile communication overhead. Continuing this direction requires refining the core-TMU interface, the Cohort queue protocol, and the OpenPiton integration, exposing practical questions about cache arbitration, queue management, batching, coherence, and software/runtime support.
\end{itemize}

\section{Extending the TMU Architecture} \label{sec:future-work-extending-tmu}

\begin{itemize}
    \item Another architectural direction is to optimize the TMU ISA and microarchitecture for dense tensor data movement. The TMU already supports dense tensor traversal, as described in \Cref{sec:tmu-programming-traversal}, but its design is primarily motivated by sparse traversal and merging. Dense tensor workloads do not require coordinate merging, but they can still benefit from efficient tiling, prefetching, and data marshaling between memory and compute units, similar in spirit to NVIDIA's Tensor Memory Accelerators (TMAs)~\cite{nvidia2022hopper}. Making dense traversal more efficient would turn the TMU into a unified access unit for both sparse and dense tensor movement, reducing hardware fragmentation and providing a common programming target for mixed sparse--dense workloads.

    \item A further architectural avenue is to extend TMU-like access units across node boundaries. Modern distributed machine learning systems spend substantial time moving data through remote memory accesses and collective operations such as \texttt{allreduce}. A distributed TMU could orchestrate remote fetches, reductions, and collective data movement, exposing communication-level parallelism in the same way that the TMU exposes memory-level parallelism within a node. The key challenges are preserving ordering, protection, programmability, and integration with existing network and runtime systems.
\end{itemize}

\section{Extending Ember} \label{sec:future-work-extending-ember}

\begin{itemize}
    \item From the compiler perspective, an important direction is to extend Ember beyond sparse--dense tensor multiplications to full sparse tensor algebra. The primary challenge is representing sparse coordinate merging in a structured form. Unlike sparse--dense embedding operations, general sparse tensor algebra often requires dynamically advancing multiple sparse fibers, which naturally introduces \texttt{while} loops and \texttt{if--then--else} constructs that do not map cleanly onto the current SLC IR described in \Cref{sec:slc-ir}. Addressing this limitation may require introducing a custom structured merge operation, extending SLC with richer control constructs, or starting the lowering from a higher-level tensor IR such as \texttt{linalg}.
\end{itemize}

Together, these directions point toward a broader vision: programmable access units and compiler support that make irregular data movement a first-class part of future processors, rather than an inefficiency hidden inside conventional cores.
